# E-5 Exploration — Per-Fact Freshness Policies

**Date:** 2026-09-02 (full-depth rewrite 2026-09-04). **Candidate:** E-5 (P1, feeds F-14 / EX-14).
**v2 author:** verification subagent. Every claim below is re-checked against code on 2026-09-04; claims are marked **[verified]** (file:line cited) or **[inferred]** (reasoned from verified evidence). Corrections vs the 2026-09-02 compact version are flagged **[CORRECTED v2]**.

**Question:** What is the freshness policy per fact class — replacing "one ceremonial pre-booking recheck" with: *recheck any fact whose cost of staleness exceeds the cost of rechecking it*?

---

## 1. Principle

Staleness is not binary and recheck is not free. For each fact class, three numbers decide the policy: **volatility** (how fast the fact rots), **staleness cost** (what breaks when it's wrong: money error, denial-of-entry, operator embarrassment), and **recheck cost** (provider call, DB read, LLM tokens, human follow-up). Policy = the cheapest mechanism that keeps staleness cost below tolerance at the moment of **consequence** (the act that would consume the fact). Consequence-time rechecking beats polling wherever the consequence moment is knowable.

## 4. Enforcement architecture sketch

**No new scheduler.** Three enforcement homes already exist; name them precisely:

1. **Consequence points = pipeline gates.** The gate protocol is already defined: `PipelineGate.evaluate(**kwargs) -> GateResult` with `GateVerdict` / `GateResult` (`src/intake/gates.py:26,35,95-97`); concrete gates `NB01CompletionGate` (:101) and `NB02JudgmentGate` (:156); dispatch-side `evaluate_autonomy_dispatch_gate(...)` (`spine_api/services/autonomy_gates.py:30`). Hard-rule blocking already flows through `ConstraintViolation(..., constraint_type=ConstraintType.HARD, severity="blocking")` (`src/decision/constraint_engine.py:246-260`). A freshness check belongs in exactly these two seams:
   - `FreshnessPolicy.assert_fresh(fact_class: str, captured_at: datetime | None, *, consequence: str) -> FreshnessVerdict` — called by `NB02JudgmentGate.evaluate(...)` (feasibility consequences: visa rule, passport, visa status) and by the constraint-engine pass (raises/accumulates `ConstraintViolation` for `stale_hard`, mirroring the existing passport pattern).
   - `FreshnessVerdict(fact_class: str, captured_at: datetime | None, policy: FreshnessPolicy, verdict: Literal["fresh", "stale_soft", "stale_hard"], reason: str)` — `stale_hard` blocks the consuming gate (money/entry classes), `stale_soft` annotates the result for the operator surface. Pure dataclass, `slots=True` per repo convention.
2. **Periodic audit = the price-lock sentinel pattern.** Keep polling only where a lock is *live* (fares during the 72h window). Generalization decision deferred (see §Decision 3). Precondition for any generalization: fix the social_inbound/strategy split-brain so one writer, one reader, one storage home **[verified defect]**.
3. **Operator surfaces.** The I-2 freshness card (`Docs/review/TPM_BLUEPRINT_TASKS_INVENTORY_2026-09-02.md:15`) becomes the generic "what's stale on this trip" view driven by the registry — reading the same `FreshnessVerdict`s the gates produced, so UI and enforcement can never disagree.

**Orphan-engine wiring (new in v2):** `PerishableSentinel.audit_perishables` should become the *classifier* the freshness layer calls when a deadline-bearing fact is written — it already produces the exact tier vocabulary (48h/12h) — and `payment_queue_service` statuses / insurance CFAR deadlines become its first item feeds. This converts F-14's zero-caller engine into the enforcement primitive without building anything parallel **[inferred, additive path]**.

**Registry as data:** the table in §3 becomes a `FRESHNESS_POLICIES` registry (per-class: TTL, trigger, consequence mapping, verdict class) so policies are configurable, auditable, and testable — mirroring how `VISA_RULES_REGISTRY`/constraint rules are packaged, but dated and owned.
