## Why these four doors

Sim #2 stress-tested ONE class: multi-actor intake merge (delegation). It
deliberately left unopened the doors shipped or ratified since:

1. **Origin Option 3 semantics** (ratified+shipped 2026-09-14: `se`/`ru` =
   fact, bare `side` = hypothesis 0.55) — probe-verified at unit level
   (10/10) but never sim-verified end-to-end in the browser pipeline.
2. **Durable customer memory** (FND-0060 closed via commit `0c6efae4`) —
   SQL agency-scoped profiles landed; no live sim has exercised them.
3. **Honest ops chain** — T6 inbound ingestion, T10 claim engine + 8-state
   disposition (`spine_api/services/claim_disposition.py:22`), T11b ghost
   concierge (`spine_api/server.py:2905`, trigger: `flight_status_updates`
   in a trip update) — all shipped in the 2026-09-29/30 waves, sim-untested.
4. **Ask-traveler loop** (T1: `POST /followups/{trip_id}/generate` → `send`
   mints a signed token → public `/a/{token}` → answers return) — shipped,
   sim-untested. Plus T9 confirmation grader.

Every persona is new (Sim #2's four adults are retired); every use case is a
different surface class: colloquial-language intake, memory, disruption ops,
accessibility + ask loop.

## Grading contract (inherited from Sim #2)

- Verbatim scripts only — no paraphrase (quoted in the personas doc).
- Every pass/fail ties to a business surface (packet field, endpoint
  response, UI element), never to cosmetic extraction.
- Zero credit for "it didn't crash".
- All defects found are registered through `scripts/findings.py` — never
  hand-edited into the store.
- Predictions are repo-fact anchored with file:line so a FAIL is a finding
  against a named expectation, not a vibe.

## Execution plan

1. Start servers (backend then frontend), verify `/health`, `/metrics`, :3005.
2. `tools/sim3_runner.py` (reusable): login (real `/auth/login` via BFF or
   direct backend), API drivers + Playwright screenshots into
   `Docs/sims/assets/sim3/`.
3. Run sims in order A → B → C → D; capture evidence JSON per sim.
4. Register findings; write `SIM3_RESULTS_2026-10-05.md`.
5. Data-safety: all seeds additive (new trips/profiles only; no TRUNCATE, no
   DELETE, no overwrite of `d1e3b2b6…` agency data).

- Payment rails (forbidden by the T10 money boundary — absence is the test).
